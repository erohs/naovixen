A tool that runs for hours still has a person glancing at it, and each glance only needs to answer a couple of questions: is it working, and is it winning? The first version of my horse-racing bot made you read every line to find either answer.

The bot is insidetrack, a side project in Python. It plays the Inside Track betting machine in GTA Online, on a PS5 streamed to my PC over chiaki-ng Remote Play. Every 40-odd seconds it captures the stream with mss, reads the six horses' odds with OpenCV and easyocr, backs one using a betting rule someone else published, reads the winner off the result screen and logs the race. Automating the game breaks Rockstar's terms of service, and accounts get banned for it. What I want to share is one piece of the engineering: the console.

## The first version

Each race printed four lines like these:

```text title="before"
[21:04:12] odds=[1, 5, 13, 4, 26, 20] trusted=True -> EVENS in lane 1
  bet MAX on lane 1 (race #7)  cycle 46.9s (race 33.1s)  rate 76 races/h
  result: lane 1 (EVENS) won -- $20,000 back on $10,000
  session: 4/7 won, $58,000 back, net +$18,000 (+25.7% ROI) -> +$392,000/h
```

All the information is there, but every line has its own shape, so your eye can't learn where anything lives. The odds are a Python list with EVENS as a bare `1`, and whether the horse won is buried mid-sentence.

## Decide what a glance is for

Each race raises four questions. Did the board read? Did the bet go on? Did it win? Is the session up? I gave each one a row with a short tag, and put every row on the same grid:

```text title="after"
time      lane     1       2       3       4       5       6
21:04:12  board    EVENS   5/1     13/1    4/1     26/1    20/1
          bet      lane 1  EVENS   MAX     10,000
          result   lane 1  EVENS   WON     +10,000
          session  1/1 won                 +10,000
          session  37.4s      +100.0% ROI  +962,567/h
```

The start-up settings shrank to one line each, flush left with the timestamps. First-run troubleshooting had been printing in full before every run, so it came out.

## One cell width for everything

Every value sits in an eight-column cell. That's the widest value, `lane 1`, plus a two-space gap. I'd started with a width per column, and each row was correct on its own terms, but the price on the `bet` row landed a character to the left of the prices on the `board` row above it. The block looked ragged. One width fixed it, for the same reason a design system has one spacing scale rather than a gap per component.

Money always starts in the same column, whether it's the stake, the race's profit, the running net or the hourly rate. Nothing runs wider than a board row, which is 64 columns, so a long message wraps onto the next line and stays on the grid. Nothing gets appended to the end of a line either: a warning or an error gets a row of its own, with its own tag.

Colour is where padding goes wrong. Python's `f"{text:<8}"` counts characters, and an ANSI escape is made of characters, so `WON` in green counts as twelve and gets no padding at all. Measure the visible width instead:

```python title="grid.py"
import re

ESCAPE = re.compile(r"\x1b\[[0-9;]*m")
CELL = 8


def visible_width(text: str) -> int:
    return len(ESCAPE.sub("", text))


def cell(text: str, span: int = 1) -> str:
    gap = CELL * span - visible_width(text)
    return text + " " * max(0, gap)
```

For the same reason, wrap text before you colour it. A line break inside an escape sequence prints the escape as literal junk.

## One bright thing per line

Each row has at most one bright value, and it's the one you scan for: the backed price on the board row, `MAX` or `MIN` on the bet row, `WON` or `LOST` and the profit on the result row, and the running net on the session row. Timestamps, tags and units are grey, so they fall back.

The `bet` and `result` rows share their cells on purpose. What you backed sits directly above what won, so you can see whether they match from the shape of the two lines without reading either.

There's no `$` on the amounts. Every figure is in the same in-game chips, so a symbol on each one says nothing, and it pushes the digits out of line as soon as a sign appears beside it.

The colour helpers are named for what they mean (`good`, `bad`, `warn`, `note`, `key`), so the palette is decided in one place and nothing else has to remember that warnings are yellow. It's the same idea as semantic colour tokens on the web. Only the eight basic terminal colours are used, so the output sits inside whatever theme the terminal already has.

Colour is always the second signal. The words `WON` and `LOST` and the sign on each profit carry the meaning, so nothing is lost when colour is off. It switches itself off when the output is piped or redirected, when `NO_COLOR` is set, or when you ask for plain text. On Windows the console understands ANSI escapes but starts with them off, so the bot switches them on once. The whole console module is in the [insidetrack repository](https://github.com/naovixen/gtacasinotrackbot).

## Numbers that move with the results

The hourly figure on the session row used to be throughput multiplied by the strategy's average return per race. It was a fair estimate, and it never moved. A session that was down still showed about +460,000 an hour. You soon learn to skip a number that ignores what just happened, and then it's only taking up space.

Now it's the session's own net divided by the time the bot has been running, not counting time paused. Over the first few races it swings hard, just as the ROI beside it does, because two races are only two races. What a given cycle time is worth in theory is a question about the timings, so it got its own command instead of a place on the live screen.
